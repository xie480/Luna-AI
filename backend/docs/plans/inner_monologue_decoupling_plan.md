# Luna AI 角色内心独白与系统校验解耦设计方案

## 1. 背景与目标

在当前的 Luna AI 系统中，大模型输出的 `thought` 字段承担了过多的“系统级任务”（如意图识别、红线审查、格式校验等）。这导致 `thought` 实际上变成了**机器的思维（Check）**，而非**角色的思维（Thought）**。

为了进一步提升 Luna 的拟人化程度，使其能够展现出“口是心非”、“傲娇”、“腹黑”等复杂的人性特征，我们需要将系统级的“规则检查”与角色级的“心理活动”进行解耦。

**核心目标：**
1. 将原有的 `thought` 字段重命名为 `check`，专用于系统级的逻辑推演与规则校验。
2. 新增全新的 `thought` 字段，专用于承载 Luna 的隐性心理活动（Inner Monologue）。
3. 在记忆系统中引入 `thought` 字段，使 Luna 能够回忆起历史对话时的真实心理状态，实现记忆的立体化。

## 2. 核心设计思路

通过引入独立的 `thought` 字段，我们构建了一个符合思维链（CoT）最佳实践的生成管线：
`Check（理性校验）` -> `Thought（感性代入）` -> `Emotion（情绪流转）` -> `Reply（最终表达）`

这种设计允许大模型在输出最终台词前，先进行充分的角色心理建设，从而自然地生成具有反差感的回复。

## 3. 详细实施步骤与文件改动方案

### 3.1 修改运行时提示词模板 (`runtime.j2`)

**文件路径：** `backend/ai-service/app/templates/prompt/runtime.j2`

**修改内容：**
1. 将“核心思维链执行要求”中的 `thought` 替换为 `check`。
2. 明确 `check` 字段的四个维度（感知与记忆、关系与情绪演算、人设演绎、绝对禁区审查）。
3. 增加对全新 `thought` 字段的定义和要求，强调其作为“内心戏”的作用。
4. 更新最终输出的 JSON 结构示例。

**具体修改细节：**
```jinja2
### 核心思维链执行要求 (Critical)
在生成最终回复（reply）之前，你必须依次进行以下推演与思考：

1. **系统校验 (check)**：你必须在 `check` 字段中【逐一、明确地回答】以下四个维度里提出的【每一个问题】。这是确保你不偏离设定的理性防线。
2. **内心独白 (thought)**：在完成校验后，你必须在 `thought` 字段中写下 Luna 当前真实的内心活动。你可以展现出傲娇、腹黑、吃醋等隐藏情绪，甚至与最终说出口的话完全相反。字数不限，内心戏越丰富，角色越生动。

（...保留原有的四个维度说明，但将其归属为 check 的要求...）

### 输出
仅输出单行 JSON，不要包含 Markdown 代码块标记。请严格按照以下结构作答：
{"check":"[感知与记忆] 意图识别：... 时间感知：... 记忆检索：... RAG与工具消化：... [关系与情绪演算] 关系动态：... 情绪状态机：... [人设演绎] 语气调优：... 内容构建：... [绝对禁区审查] 身份红线：... 格式红线：... 真实性红线：... 括号红线：...","thought":"（Luna真实的内心活动，第一人称，可与回复产生反差）","emotion":"<枚举情绪>","reply":"<回复内容>"}
```

**具体修改细节：**

### 3.3 后端代码调整说明

#### 3.3.1 流式解析器适配 (`stream_parser.py`)
**文件路径：** `backend/ai-service/app/llm/stream_parser.py`
**修改说明：**
* 更新 JSON 流式解析的状态机逻辑。
* 原有的解析顺序为 `thought` -> `emotion` -> `reply`。
* 需要修改为依次解析 `check` -> `thought` -> `emotion` -> `reply`。
* 确保 `check` 和 `thought` 字段在流式输出时被正确缓冲和跳过（或根据需求选择性地发送给前端作为彩蛋）。

#### 3.3.2 记忆片段组装逻辑适配 (`context_manager.py` 或相关记忆处理模块)
**文件路径：** `backend/ai-service/app/llm/context_manager.py` (或负责组装 `MEMORY_SNIPPETS` 的模块)
**修改说明：**
* 在从数据库拉取历史聊天记录并格式化为文本注入到 `{{MEMORY_SNIPPETS}}` 时，需要将数据库中存储的 `thought` 字段一并格式化输出。
* 格式化模板应调整为：
  ```python
  f"[{time}] \nUser: {user_msg}\nLuna (内心): {thought}\nLuna (回复): {reply}"
  ```

#### 3.3.3 数据库与数据结构适配 (Go Runtime 层)
**文件路径：** `backend/runtime/internal/repository/models.go` 及相关 DB 操作文件
**修改说明：**
* **PostgreSQL**: `chat_history` 表需要新增 `thought` 字段（类型为 `TEXT`），用于持久化存储每轮对话的内心独白。
* **Redis**: 缓存的短期上下文结构中也需要增加 `thought` 字段。
* **Proto/Schema**: 更新前后端及 Go-Python 之间的通信协议（如 `communication.proto`），在消息结构体中增加 `thought` 字段（可选，如果前端需要展示内心戏彩蛋）。

## 4. 预期收益与风险评估

**预期收益：**
* **角色深度提升**：Luna 将具备真正的“灵魂”，能够展现出复杂的心理活动和反差萌。
* **回复质量提升**：通过 CoT 机制，大模型在生成回复前有更充分的上下文铺垫，减少 OOC。
* **记忆立体化**：带有情绪和心理活动的记忆将使长程陪伴体验更加真实。

**风险评估：**
* **Token 消耗增加**：新增的 `check` 和 `thought` 字段会增加输出 Token 数量，可能导致生成延迟略微增加。
  * *缓解策略*：在本地部署场景下，可接受轻微的延迟增加以换取质量提升；可优化流式输出体验，在生成 `check` 和 `thought` 时前端展示“Luna 正在思考...”的动画。
* **旧数据兼容性**：数据库新增字段后，旧的聊天记录将没有 `thought` 数据。
  * *缓解策略*：在组装记忆片段时进行判空处理，如果旧记录没有 `thought`，则按原格式输出。
